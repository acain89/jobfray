# JobFray recurring financial processing and public activation

## Processing contract

The dedicated `financial` worker mode runs independently of `JOBFRAY_CHECKOUT_ENABLED`. It requires verified persistence and production provider gates. `JOBFRAY_REFUND_PROCESSING_ENABLED=1` separately permits only corrective refunds derived from immutable verified payment events, a matching JobFray request and one of the application reasons: missing allocation, amount mismatch, duplicate charge, expired hold or unavailable business. Arbitrary manual refund records fail closed.

Every minute, the existing authenticated Cloudflare JobFray cron calls `/api/worker` with `x-jobfray-worker-mode: financial`. The Render environment must contain `JOBFRAY_WORKER_MODE=financial`. Cloudflare `SCHEDULER_MODE=financial`, `SCHEDULER_ENABLED=1`, `ACCEPTANCE_ENABLED=0` and `WEBHOOK_INGRESS_ENABLED=1` retain maintenance and closed operator access. The route continues requiring its independent worker bearer and trusted ingress. It does not run retention, historical deletion or media cleanup.

A durable `financial-worker:minute` execution record serializes scheduled runs using an advisory lock, unique lease token and 15-minute crash-recovery lease. Each run handles at most five payment operations, five refund candidates, 100 expired holds and five notification attempts. Per-operation leases and tenant/payment locks protect reconciliation and fulfillment. Holds are cleaned after payment reconciliation; late payments produce authorized refund work rather than resurrect expired capacity. Existing confirmed/released records are excluded.

Payment operations and refunds stop after 20 claims/attempts. Transient failures back off from approximately one minute to one hour. Refund creation keeps the original row-specific idempotency key across retries, refuses ambiguous creation after 23 hours, polls an already saved refund ID instead of creating again, checks event/request/amount binding before creation, and fences stale results by lease token. Duplicate refund rows for a payment cannot create separate refunds. Failed or disputed work requires operator review, not blind retries or financial-record edits. A run-level failure is durably marked and may retry next minute; item-level limits remain intact.

Review the latest `financial-worker:minute` document and sanitized cron log for `DONE`, the deployed commit, `source: cron`, scheduled/completed times and zero failed financial alerts. A skipped run while another owns an unexpired lease is expected; persistent skips beyond the lease or missing consecutive completions require investigation. Do not reset failed attempts or replay uncertain provider writes without authoritative readback and a reviewed disposition.
