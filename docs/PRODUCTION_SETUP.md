# Production setup and recovery

This is a preparation runbook, not authorization to provision, connect, deploy, change DNS, or transact. Stripe must remain disconnected until separately authorized. See PROVIDER_CONFIGURATION.md for every exact environment variable and account requirement; use production.env.example as a placeholder manifest.

## Environments and gates

Use completely separate local sandbox, provider staging and production identities, databases, sending domains, image clouds, signing secrets and webhook secrets. Never reuse RF/RFL resources. Local mocks require explicit loopback-only sandbox configuration and are forbidden in deployment. The production runtime selects Prisma and configured adapters only; it never substitutes FileRepository, MemoryRepository or mocks.

All release/operation/indexing/checkout flags default to `0`. Build-time validation is pure and performs no provider authentication. Invalid enabled configuration aborts startup. Configure the actual canonical origin and build-time VAPID public key before building; changing build-time public configuration requires a new build. Configuration validation is not proof that credentials work.

`/api/health` reports process liveness. `/api/ready` stays 503 without verified database/provider gates and operation authorization; once explicitly enabled it also performs a bounded persistence read. It does not execute a financial/provider test as a health check. Monitor provider failures separately.

## Ordered deployment procedure: future authorization required

1. Review the Phase 5 report and release checklist. Obtain explicit permission for each external account, staging interaction, migration target, deployment and DNS/TLS operation. Nothing in this repository grants that permission.
2. Create new environment-specific provider resources and approved hosting plans. Configure sender authentication, Geocodio US forward-geocoding access under the reviewed data-source terms, and authenticated Cloudinary assets. Perform an independently authorized staging contract/interoperability exercise. Keep actual production checkout off.
3. Establish the trusted ingress. Strip untrusted JobFray assertion headers, derive the real client IP at the trusted boundary, and inject `x-jf-edge-secret` plus `x-jf-client-ip`. Prevent bypass to the origin. Do not simply trust arbitrary X-Forwarded-For. Verify missing/wrong assertions fail closed, legitimate customer requests work, and direct-origin traffic cannot bypass abuse limits.
4. Create a NEW private PostgreSQL service and separately scoped migration-owner and application roles. Do not automatically supply an owner connection string to the web service. Verify database identity, TLS/private connectivity, backup destination, region and restore target. Render documents support for cube, earthdistance and pg_trgm; permissions and actual extension behavior must still be checked on the chosen instance. [Render supported extensions](https://render.com/docs/postgresql-extensions).
5. Take a verified encrypted backup and perform an isolated restore rehearsal. Use the migration-owner URL only in a separately authorized migration job. Run `node node_modules/prisma/build/index.js migrate deploy`. Never run reset, db push or seed. Existing historical files must not be changed. Check migration ledger, CHECK constraints, triggers, compound foreign keys, expression/partial indexes and directory backfill. Prisma's empty diff does not verify SQL-only guards.
6. Grant only the necessary Jf table access to the application role. No superuser, schema/function creation, role/database creation, TRUNCATE, trigger-disable, replication, or access to legacy tables. Snapshot/event/audit tables require SELECT/INSERT only; no UPDATE/DELETE. Requests and refunds must not be deleted. Other Jf tables require service writes and limited retention deletes. The directory projection's triggers execute as the application role and require its projection INSERT/UPDATE/DELETE privileges. Install extensions and functions using the migration role; revoke public schema CREATE from untrusted roles.
7. Build from the reviewed commit with `npm ci`, `npm run db:generate`, `npm run typecheck`, `npm run lint`, `npm test` and `npm run build`. Supply verified canonical settings at build time. Review a fresh dependency audit and run staging database, HTTP, browser and provider checks. Do not use the disposable test cluster as a deployment database.
8. Deploy a NEW web service from the reviewed branch only after explicit authorization. Start with `npm run start -- --hostname 0.0.0.0 --port $PORT`. Use `/api/health` for initial liveness while gates are closed; keep `/api/ready` in release monitoring. `docs/render.example.yaml` is intentionally a non-deployable review template with placeholder plans and disabled operations. Supply the complete manifest separately. [Render Blueprint fields](https://render.com/docs/blueprint-spec).
9. Arrange canonical and business wildcard DNS/TLS only after separate approval. Validate canonical host, reserved subdomains, secure cookies, redirects, mobile layout, confirmation privacy, protected media, real ingress and webhook raw-body delivery. Custom domains remain a separate verification project. No DNS/certificate operation was performed here.
10. Configure authenticated scheduling to POST `/api/worker`. The prepared `scripts/production-worker.mjs` reads only canonical origin/host, the worker secret and explicit operation authorization. A cron service can run it once per minute; monitor runtime and backlog, and tune cadence after measured staging behavior. The client has a ten-minute timeout; individual adapter calls time out after eight seconds. A failed scheduler client does not prove that server work was rolled back. Server-side durable leases and idempotency govern recovery. Render cron is documented at [Cron jobs](https://render.com/docs/cronjobs).
11. Enable persistence and configured adapters only after acceptance. Actual outbound operations require their own explicit operation and provider-verification gates. Production card payment tests, refunds, business email/push, uploads and geocoding need their own permissions. Verify account/environment/amount binding and signed event handling before setting `JOBFRAY_CHECKOUT_ENABLED=1`.
12. Obtain legal and provider review of Terms, fee/refund disclosures, privacy/retention. Only after a separately approved verified production release enable public indexing and assess real readiness. Keep checkout disabled if any essential control fails.

## Worker, reconciliation and operator handling

The worker handles provider session/event reconciliation, expiry, refund-required processing, retention/deletion and the notification outbox. Provider calls remain outside database transactions. Claims and per-item renewals are short database transactions; stale ownership cannot acknowledge a newer lease. Serializable transactions retain bounded retries and sorted tenant/payment locks. No global lock is held during external I/O.

Inspect authenticated admin operation alerts, refund states and sanitized `jobfray.worker_attention_required` events. Monitor pending-job age, FAILED jobs, provider timeout/rate-limit rates, refunds needing action, notification backlog, cleanup backlog, serializable retries and retry exhaustion. The protected admin overview returns a bounded alert page; it is not a provider administration console.

Successful payment after internal hold expiry cannot confirm a booking; it produces refund-required remediation. Replaying a completion event or reconciliation must not create another allocation, request or charge. Lost provider-creation responses are recovered through prepared checkout identity and a canonical verified event. Never manually mark a browser return as paid. Never recreate a session/refund under a new key merely because a call timed out.

Stripe refund creation without a durable provider ID stops automatic retry after 23 hours; reconcile against the original payment/provider records before any operator action. Pending refunds with an ID are status-polled. Failed/canceled refunds create operator-visible failed refund state. Dispute events create durable alert/audit records; response evidence and provider actions remain authorized operator responsibilities. Independent business nonperformance is not an automatic JF refund reason.

Resend retries use the stable outbox key within its documented idempotency period. An uncertain send older than that period requires operator reconciliation rather than blind resend. Confirmation/dashboard records remain authoritative if notification delivery fails. Push remains best-effort and optional.

## Customer checkout and confirmation

Customers enter a contact phone once and affirm its accuracy in an accessible modal before checkout. This does not verify ownership and grants no authorization. Request capabilities are random, stored hashed, limited to a business/browser and expire after one hour. Browser limits supplement the existing trusted-edge limits: capability issuance 30/15 minutes, first checkout attempts 10/15 minutes per browser/business, and quote uploads 12/15 minutes per browser, with six assets per capability. Idempotent replay does not consume the first-checkout budget. The separate HttpOnly, SameSite browser cookie is required for uploads and checkout. Idempotency replay is bound to the original browser; quote assets cannot be attached to another request. Fee review creates no hold; checkout rejects stale/tampered accepted pricing rather than silently charging a different fee. Dismissal or editing the phone does not initiate checkout.

Customers must save their confirmation or copy the protected fragment link. No customer delivery provider is required. Existing paid confirmations remain accessible through their original capabilities. Existing retired notification/token history is not migrated away; workers select only supported business email/push channels.

## Retention and recovery

Unpaid quote images expire at 24 hours; confirmed quote images at 180 days. Durable Cloudinary deletion jobs survive row cleanup and retry outside transactions. Unreferenced business images become eligible at 24 hours; cleanup walks bounded keyset batches and protects draft, publication and offering references. Monitor lag; eligibility is not a promise of instantaneous provider erasure. Timed-out uploads have one-hour orphan cleanup jobs. Do not erase payment, refund, audit, snapshot or confirmed-obligation history as part of image/account cleanup.

Back up database state, provider references, migration ledger and signing-key versions to encrypted access-controlled storage. Schedule regular restore drills into a distinct isolated target and compare immutable snapshots, payment events, confirmed allocations, private media references and representative confirmation access. The Phase 5 local restore used synthetic data only; production backup/PITR, encryption and retention remain unverified.

For interrupted processing, restore service access and run authenticated workers; reconcile the original provider identities and durable event/operation states. Do not reset financial queues or discard unknown outcomes. If persistence is unavailable, disable new checkout first and preserve existing obligations. In corruption incidents, stop new writes and reconcile provider events before a reviewed restore. Never restore a stale backup while continuing to accept payments.

## Rotation and rollback

Rotate provider keys in each environment independently, validate them under separate authorization, then revoke old keys after outstanding operation reconciliation. Webhooks accept multiple signing secrets during overlap. Rotate worker/edge secrets with coordinated ingress/scheduler changes and deny old secrets after cutover. Rotate VAPID keys with device resubscription; do not expose private keys. Session tokens are opaque database-backed random capabilities; revoke sessions on compromise and rotate confirmation signing versions without losing required historical keys. Previous-key configuration supports eight old versions; preserve archived keys and plan retirement/replay compatibility before exhausting that bound.

Roll back application traffic only to a schema-compatible reviewed commit, or disable new checkout. Keep additive tables and financial history intact; use forward repair migrations. The provider/projection tables and Phase 6A insert guards require a compatible application. Retired contact-token and delivery creation is intentionally rejected; verify backward behavior before any rollback. No destructive database rollback commands are supplied.

## Security limits requiring release review

The enforced CSP restricts origins, framing, forms, objects and connections, but retains inline script/style allowances for the current Next rendering/theme implementation. This is not a nonce-based CSP or a claim that XSS is impossible. Obtain independent review, validate real trusted ingress and origin isolation, and exercise external-provider failure behavior before public financial release. Browser automation is Chrome on Windows, not a Safari/iOS, Firefox, screen-reader or legal/provider certification.
